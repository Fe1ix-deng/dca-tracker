# 单独删除计划设计

## 背景

用户误创建计划后，目前只能在设置页使用“清除所有数据”，这会同时删除全部计划和历史记录，风险和影响范围都过大。需要提供针对当前计划的单独删除能力。

## 目标

- 在设置页当前计划的操作区提供单独删除入口。
- 删除前要求用户确认，取消时不改变任何数据。
- 删除计划时同步删除该计划对应的历史记录。
- 保留其他计划及其历史记录。
- 删除当前计划后自动选择剩余计划；删除最后一份计划后进入无计划状态。

## 非目标

- 不改变计划编辑、创建、导入导出或“清除所有数据”的行为。
- 不增加独立的计划管理弹窗或顶部下拉框管理功能。
- 不提供删除后恢复能力；现有 JSON 备份仍是恢复手段。

## 交互设计

在 `设置` 页已有的“撤销修改 / 填写新计划”操作区增加“删除当前计划”按钮。按钮使用现有破坏性操作样式和删除图标，只有存在已保存计划时显示。

点击后显示确认提示，内容明确说明当前计划名称及其历史记录会被删除，且操作不可撤销。用户取消确认时保持当前表单和持久化数据不变。

确认后删除当前计划及其 `planId` 对应记录。若仍有其他计划，活动计划切换到剩余列表中的第一份，并显示该计划；若没有剩余计划，清空活动计划并停留在设置页的空状态。

## 数据流与实现边界

在 `usePlan` 中新增 `removePlan(planId)`：

1. 从规范化计划列表中移除目标 ID。
2. 根据剩余列表计算新的活动计划 ID；若被删计划不是当前计划，则保持原活动计划（如果仍存在）。
3. 持久化计划列表、活动计划 ID 和兼容用的单计划存储键。
4. 返回新的计划状态。

App 层新增删除处理器，调用 `removePlan` 并过滤 `records` 中目标 `planId`，持久化变更时间，切换到设置页。Settings 接收删除回调并负责确认提示及表单重置。

## 错误与边界

- 没有当前计划时不渲染删除按钮，也不调用删除回调。
- 传入不存在的计划 ID 时不删除记录，状态保持不变。
- 删除当前计划后不能让活动计划 ID 指向已删除计划。
- 删除计划和对应记录需在同一用户操作中完成，避免留下孤立历史记录。

## 测试策略

- `usePlan`：删除非当前计划、删除当前计划并切换、删除最后一份计划、目标 ID 不存在。
- `App`：确认删除后仅移除目标计划及其记录，并标记数据已变更；取消确认不变更状态。
- `Settings`：删除按钮仅在编辑已有计划时显示；确认和取消分支；确认文案包含计划删除和历史记录影响。
- 运行现有完整测试套件，确保创建、编辑、切换和清除全部数据不回归。
